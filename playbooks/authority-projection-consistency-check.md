# 权威↔投影一致性机械校验

> 理念出处：唯一事实源与投影（DSH）+ Fowler「机械化执行胜于口头约定」。
> 本手册的每一步都在真实仓库红→绿演练过：首个版本拦截了 5 处真实旧路径漂移后才转绿。

## 一、解决什么问题

当一个系统同时存在「机器读的结构化定义」和「人读的说明文档」时，两者靠人工同步，
历史上必然产生两类漂移：

| 漂移类型 | 实例 |
|---------|------|
| 数值错绑 | 散文/表格把「规则 X 的存量基线」写成另一个规则的数字 |
| 幻影引用 | 文档宣称事实源在某个文件（实际已删）、或出现指向不存在路径的链接 |

口头约定「改了代码记得同步文档」无效。解法：写第 5 个工件——一个机械校验器，
把「投影必须等于权威」变成确定性断言，挂进 CI/门禁。

## 二、适用场景判定

满足以下条件才值得建这类校验器，否则收益不抵维护成本：

- 权威定义是**代码内的结构化数据**（规则表、枚举、常量），可用轻量解析提取；
- 投影文档有稳定格式（markdown 表格或约定式散文短语），可正则抽取绑定；
- 漂移曾真实发生过或代价高（比如基线数字错了会让整个质量门失真）。

典型落点：架构约束检查器 ↔ 约束文档、CLI 参数表 ↔ 使用手册、错误码表 ↔ FAQ。

## 三、核心模型（一张图）

```
权威（SSOT，代码内）            投影（人读，md）
┌──────────────────┐           ┌──────────────────┐
│ RULES = [         │   同步    │ | X-Wn | 基线 N | │
│   Rule(id=...),   │ ────────> │ `Y-Wm`(基线 M)    │
│ ]                 │  （人工）  │                  │
└──────────────────┘           └──────────────────┘
          ▲                            │
          └────── 机械校验器断言两者相等 ──┘
```

铁律：**修改顺序只能是「先改权威（代码），再同步投影（文档）」，禁止反向迁就。**
校验器发现不一致时报错的对象永远是「投影没跟上」。

## 四、实施六步（Python 正则扫描示例）

### 步骤 1：解析权威侧，建立全局注册表

从各检查器源码中按块解析规则定义，得到 `{rule_id: (level, baseline)}`。

```python
rules = {}
for block in re.split(r"lib\.Rule\(", text)[1:]:
    m_id    = re.search(r'id\s*=\s*"([A-Z]-[EW]\d)"', block)
    m_level = re.search(r'level\s*=\s*"(ERROR|WARN)"', block)
    m_base  = re.search(r"\bbaseline\s*=\s*(\d+)", block)
    rules[m_id.group(1)] = (m_level.group(1),
                            int(m_base.group(1)) if m_base else None)
registry.update(rules)
```

要点：一条规则在任何一处定义，全局只能有一个登记项（dict.update 天然去重）。

### 步骤 2：先校验权威侧自身的内部自洽（H-E2）

在对比投影之前，先让权威侧满足不变量——这是最常见的偷懒点：

- `ERROR` 级规则**不得**显式携带非零 baseline（语义恒 0：红线不允许存量）；
- `WARN` 级规则**必须**携带 baseline 参数（基线棘轮，只降不升）。

解析不到任何规则定义、或扫描根路径缺失时，检查器应立即以 `exit 2`（脚本自身错误）
退出，而不是继续输出「通过」。

### 步骤 3：从投影文档抽取绑定（两种形态都收）

```python
# 形态 A：表格行 | `X-Wn` | …… | **N** |
TABLE_ROW_ID   = re.compile(r"^\|\s*`([A-Z]-[EW]\d)`\s*\|")
TABLE_BOLD_NUM = re.compile(r"\*\*(\d+)\*\*")

# 形态 B：散文 `X-Wn`(基线 N)，限制跨距且不许吞掉下一个规则 ID
PROSE_BINDING = re.compile(
    r"`([A-Z]-[EW]\d)`(?:(?!`[A-Z]).){0,48}?基线\s*(\d+)")
```

同一条规则的多个绑定候选要全部收集（带行号），逐个比对，报错时能指出具体位置。

### 步骤 4：audit 主文档 + 共享文档，三类检查分工

```python

    nums, refs = collect_bindings(rel)

```

### 步骤 5：区分「域主文档」与「跨端共享文档」（来自真实返工）

首个版本把一篇跨端共享的原则文档划进 java 和 ts 两个域分别做完整性检查，
结果另一端的规则 id 在本文档中出现就触发「未知规则」误报。正确建模：

- **域主文档**：参与 H-E3 完整性（本域 WARN 必须 100% 登记）；
- **共享文档**：进入全局注册表，只查 H-E4/H-E5（其中的绑定必须成立，但不要求穷尽）。

先花 10 分钟想清楚「哪些文档对哪些规则承担登记义务」，能省掉一轮结构性返工。

### 步骤 6：空解析保险——绝不让正则失效冒充全绿

```python
if bindings_total < script_warn_total:
    print("解析到的绑定 %d 处 < 脚本 WARN 规则 %d 条，检查器自身失效"
          % (bindings_total, script_warn_total))
    return EXIT_SELF_CHECK_FAIL   # 2
```

没有这道保险，一次无害的正则改动就能让所有检查静默变成 no-op，门禁形同虚设。

## 五、守卫有效性演练（红→绿）

守卫只有真拦过回归才算守卫。上线前必须完成一轮人造红灯：

1. **天然红**：故意留一处旧路径/旧基线，跑检查器，确认拦截并输出准确位置；
2. **转绿**：修完所有命中，重跑到 0 违规；
3. 观察误报：每一个误报都是建模缺陷（实测两次：共享文档归属错误、
   自己新写的解释性注释里含字面量被拦——见下节）。

## 六、已知边界与坑点

| 坑点 | 说明 | 对策 |
|------|------|------|
| 守卫拦自己写的注释 | 在文档里举例说明旧路径形态时，例子本身被红线扫中 | 改写措辞消除字面量，**不要**为特例给规则开口子 |
| 语义错绑检测不到 | id 与数字各自合法、但配错了对（如把 A 规则的基线写在 B 的行） | 保持「先权威后投影」单向修改纪律 + 变更时人工对照 diff 兜底；此为数值校验的理论盲区 |
| 基线棘轮只降不升 | 有人想通过上调 baseline 让失败变绿 | 流程上约定调基线必须连带改代码减少违规数，评审时盯这个方向 |
| 表格加粗列扩展 | 未来在行内加第二个加粗数字会被 search 取首个命中 | 用 finditer 收集全部数字并要求其中恰有一个匹配基线，或固定列为命名锚 |

## 七、退出码契约与接线

与其余检查器统一三态：`0` 通过 / `1` 存在违规 / `2` 检查器自身错误（含空解析保险触发）。
把它追加进总门禁的 CHECKERS 注册数组，与其他领域检查器一起被全量命令触发，
避免「有了守卫但没人记得跑」的第五种漂移。
