架构质量门的存量冻结模式（legacy-freeze 快照） ​

适用场景 ​

  • 项目里有确定性静态检查器（自研正则扫描 / lint 规则 / arch-check），但存量代码违规数量巨大 （继承的旧脚手架、上游框架、历史脚本），导致质量门从引入之日起就永久红灯；
  • 团队决策是**「不为历史包袱兜底」**：不安排偿还工时，不想让旧债阻塞新代码的门禁；
  • 同时不能放弃护栏：新增代码违规必须被一票拦下。

典型症状：arch-check-all 里某条规则（如 SQL 列级 COLLATE 声明）命中 192 处全是旧脚本， 每次跑门禁都失败，大家开始习惯性忽略退出码——门禁名存实亡。

为什么不用「基线棘轮」 ​

基线棘轮（允许 ≤N 命中、只降不升）看似合理，但实战暴露三个问题：

  1. 永不归零即永久黄灯：没人偿还时 N 永远大于 0，门禁输出永远带失败色，注意力被稀释；
  2. 计数语义模糊：棘轮只看总数，「同文件删一处旧违规 + 加一处新违规」总数不变，新增被放过；
  3. 触发刷基线的冲动：每次总数上升都要人肉判断「是新增还是扫描面变化」，成本高且易被「顺手上调基线」侵蚀。

存量冻结把「旧债豁免」从数量阈值变成文件级快照，一次性、显式、可审计。

机制设计 ​

数据结构（冻结清单 legacy-freeze.json） ​

json
{
  "_meta": { "frozen_at": "2026-09-01", "policy": "存量整体冻结豁免，新增即违规" },
  "rules": {
    "J-W4": { "total": 33, "files": { "jp-console/.../Foo.java": 2 } },
    "S-E2": { "total": 192, "files": { "jp-console/db/202607/DDL/xxx.sql": 17 } }
  }
}

按「规则 → 文件 → 数量」三级结构，粒度到文件，总量校验用 total。

判定口径（核心算法） ​

  • 新文件（不在冻结清单内）：所有命中全量计为新增；
  • 老文件：命中数 ≤ 冻结数 → 全部豁免；超出冻结数的部分计为新增；
  • ERROR 与 WARN 同口径：豁免只豁免存量，规则等级语义不变；
  • 允许的新增数恒为 0，退出码语义保持：0 通过 / 1 有新增违规 / 2 脚本自身故障。
python
def _split_new_hits(found, frozen_map):
    per_file = {}
    for item in found:
        per_file.setdefault(item[0], []).append(item)
    new_hits, frozen_total = [], 0
    for rel_path, items in per_file.items():
        frozen = min(frozen_map.get(rel_path, 0), len(items))
        frozen_total += frozen
        new_hits.extend(items[frozen:])
    return new_hits, frozen_total

输出行必须同时展示三个数：命中 N（存量冻结 F 新增 X）允许 新增=0——让人一眼看出豁免规模，防止「门禁在放水」的误解。

实施步骤 ​

  1. 政策先行：先和决策人明确三件事——存量豁免范围（全量 or 白名单）、偿还是否为义务（建议否，通道保留）、 新增违规的处置（一律拦）。把结论写成显式政策条款（如 refactoring-rules 的「历史包袱政策」三节）， 政策没定之前不要动代码；
  2. 写生成器 freeze-legacy.py：复用检查器的扫描函数逐规则落盘快照。两个安全设计不可省：
    • 默认拒绝覆盖：清单已存在时 exit 2，必须 --force 才重建（防智能体刷清单掩盖新增）；
    • 清单缺失时响亮失败：检查器在 freeze_path 给定但文件不存在时 exit 2，绝不静默降级为「全量豁免」或「全量拦截」；
  3. 检查器接线：run() 增加 freeze_path 参数，替代原基线逻辑；检查器自身不含任何硬编码豁免名单， 豁免数据只来自清单文件（单一事实源）；
  4. 生成并固化清单：python freeze-legacy.py 生成 → 提交进 git → 之后把该文件列入「禁止改写」红线；
  5. 文档同步：所有提到「基线 / 允许 N 条」的文档全部改为「存量冻结 F、新增即违规」口径， 冻结数以清单为准（文档写死数字会漂移，注明来源是清单）；
  6. 状态收编：把「偿还旧债」型的待办（feature / debt 条目）标记关闭并在 resolution 写明 「被政策抵消关闭」，pi 项标 resolved（有动作的）或 accepted（纯接受的），不留悬空状态。

验证协议（缺一不可） ​

  1. 正向全绿：arch-check-all 四端 exit 0，且此前被存量阻断的规则（如 S-E2=192）首次通过；
  2. 负向红测：注入一个含已知违规模式的临时文件（如 console.log）→ 对应检查器 exit 1 且 「新增 1」→ 删除文件后复绿 exit 0。没有红测的门禁改造等于没验证——存量冻结最容易改出 「全量豁免」的假绿；
  3. 钩子冒烟：接入 post-edit 钩子的（编辑后自动跑单端检查器）跑一遍确认退出码正常；
  4. 清单精确性核验（2026-09-01 对抗式审查补）：逐条比对每条规则的「命中数 == 冻结数」。 清单虚高（登记数 > 实际命中数）不会让任何检查失败——min(frozen, len(items)) 截断后 新增为空照样全绿，但虚高部分是静默漏拦额度：未来等量的新增违规会被无声放过。 这是全绿门禁自身查不到的盲区，只能人工比对总数发现（实战：QCM V2 的 11 条有命中规则 全部 6/6、19/19、192/192、82/82 逐一相等，清单不虚不漏）。清单遗漏（登记数 < 实际数） 反而安全——超出部分会被报为新增，门禁直接拦下。

已知取舍（诚实标注） ​

  • 同文件内等量置换不可见：老文件删一处旧违规 + 加一处新违规，命中数等于冻结数，判为全豁免。 这是文件级粒度的固有限制，接受；补救靠 review 人工兜底；
  • 删光老文件里的违规不会自动缩表：清单数字是静态快照，偿还存量后清单与实际偏差只影响 「frozen 计数展示」，不影响拦截能力（新文件仍然全量计）；如需刷新，走 --force 且必须立即全绿；
  • 清单是新的腐化点：它本身成为最高风险文件（被改写 = 门禁失效），必须列入每周巡检的 git diff 必看项。

扫描面收缩时的合法重建（2026-09-01 补） ​

移出某端支撑（如冻结整个移动端工程、删除其检查器）会让检查器集合与清单规则集变化， 此时重建属政策允许的「人工确认基线重建」第三种合法场景，操作要点：

  1. 先改代码再重建：先移除聚合器 / 生成器 / 门禁脚本里的对应检查器项，最后才 --force 重建清单 （顺序反了会把已删检查器的规则残留进清单）；
  2. 重建前后逐条比对：其余端每条规则的冻结数必须逐条不变——实战口径：597→588 处 / 12→11 条规则， 减少的 9 处 / 1 条全部来自被移除的端，Java/SQL/TS 三组数字逐一核对无漂移；
  3. 任何「其余端数字也变了」都是红灯：说明重建动作本身掩盖了真实新增（或扫描面判断有误）， 必须停下查清，不允许带着漂移继续；
  4. 重建后立即跑全量检查，须全绿；门禁脚本（如 fast-gate 的端开关）同步删掉对应项并冒烟。

配套决策（「仅去支撑、工程保留」模式）：工程目录与后端为其服务的接口（如 /app/**）保留不动， harness 导航文档里给冻结注记（「无检查器 / 门禁 / 条文，任务涉及时先转人确认」）， 工程画像留在状态文件里标 _frozen_note 供未来重启时参考。

偿还后的棘轮收缩（2026-09-07 补） ​

存量被真实偿还（如某 MR 修复移除了某文件的全部命中）后，清单登记数会虚高于实际命中数—— 虚高不报错、只静默漏拦（见验证协议第 4 条），此时不要 --force 重生成（会把期间其他变化 一并刷进清单，失去审计性），正确操作是手工只降不升收缩：

  1. 强验证定位差异：写临时脚本复用检查器同口径的扫描函数，逐文件比对「实际命中 vs 冻结登记」， 找出登记虚高的确切文件与数量（虚高是全绿门禁自身查不到的盲区，只能人工比对发现）；
  2. 手工删条目 / 降数量：只动差异项（如该文件登记 1 → 删除该 key），其余一律不碰；
  3. _comment 棘轮登记：在清单说明里追加一行「日期 + 任务 + 哪条规则哪个文件从多少降到多少 + 总数变化」，显式声明这是合法收缩而非重生成——审计时可区分「人工收缩」与「掩盖新增的改写」；
  4. 收缩后立即复跑全量门禁：命中数与冻结数重新相等（如 S-W2 命中 230 = 冻结 230）且全绿 exit 0 才算完成。

实战案例：QCM V2 harness task-014 gc（2026-09-07）——MR !29 修复移除 scm备案供应商字典.sql 唯一存量别名后，S-W2 冻结 231→230、总数 588→587，_comment 登记 + arch-check-sql 复跑全绿。

踩坑注记 ​

  • 共享库 load_sibling() 若按「stem + '.py'」拼接路径，调用方传 arch-check-java.py 会得到 arch-check-java.py.py 报 FileNotFoundError——生成器里引用兄弟脚本时传不含扩展名的 stem；
  • 冻结清单含中文路径时，写盘用 json.dump(..., ensure_ascii=False, indent=2, sort_keys=True)， 排序让 git diff 稳定可读；
  • 检查器与生成器对「扫描根 → 相对路径」的计算必须同源（共用一个函数），否则清单 key 和扫描 key 对不上，豁免静默失效、全量误报新增。
